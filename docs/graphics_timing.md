# HQCDD 이동 속도 조사 (2026-09-10)

사용자는 GDI와 D3D11 모두 혼자하기 전투의 이동이 예전 기억보다 빠르다고 보고했다.
같은 PC에서 원본 실행본과 동일 조건을 비교한 결과는 아직 없다.
조사 시점에는 게임이 종료되어 실제 틱 속도는 측정하지 못했다.

## 확인된 원본 코드

분석 EXE SHA256:
`6c0597be236fc5c803b130bed6ae6ce19698b1b4b58af8b790c41b9560e5cea8`.

- `0x42334a`: `_INMM.dll!_imeGetTime`을 호출하고 `0x9b5210`에 현재 시각 저장.
- `0x41c879`: 실전 업데이트에서 `0x41c970` 시간 판정 함수 호출.
  반환값이 0이면 업데이트를 건너뛴다.
- `0x41c970`: 현재 시각과 직전 틱 시각(`0x61d9c0`) 차이를
  속도 설정 함수 `0x4165c0`의 간격 및 보정값과 비교한다.
- `0x41c8c0`: 위 판정을 통과하면 진행 카운터 `0x8924b8`을 증가시킨다.
- `0x4165c0`: 일반적인 로컬 플레이에서 `0x6695a4`의 속도 옵션에 따라
  기본 간격(`0x4ed80c`, 파일 초기값 50ms)에 +14, +10, 0, -10을 적용한다.
  범위 밖 옵션은 -20이며 일부 다른 상태에서는 60ms 또는 기본 간격을 반환한다.
  화면상의 옵션 이름과 값 대응은 아직 확인하지 않았다.
- `0x4246da`: 다른 단계 처리 루프에는 별도로 최소 50ms 간격이 있다.
  이 값은 모든 실전 시뮬레이션의 고정 간격이 아니다.

즉 실전 업데이트에는 이미 시간 제한이 있다. 래퍼의 출력이 빨라졌다는 이유만으로
게임 시뮬레이션이 무제한 진행한다고 단정할 수 없다.
원본 그래픽 경로의 대기로 실제 진행이 설정 속도보다 느렸을 가능성과 속도 설정 차이,
체감 차이는 아직 구분되지 않았다. `WaitForVerticalBlank`의 단순 Sleep(1)은
래퍼의 호환성 한계지만 이번 이동 속도 증상의 원인으로 확정되지 않았다.

## 재현 도구

읽기 전용 디스어셈블:

```powershell
uv run --with pefile --with capstone python tools/re_graphics_timing.py '<원본 EXE>' --start 0x41c970 --size 0x80
```

실행 중 게임의 확정된 타이밍 필드만 읽는 샘플러:

```powershell
python tools/sample_syw2_timing.py <게임 PID> --seconds 10
```

알려진 원본 또는 import만 바꾼 HQCDD 실행본의 해시를 확인한 뒤 메모리를 읽는다.
메모리 쓰기, 프로세스 중단, 시계 변경은 하지 않는다.
같은 맵·게임 속도·유닛·목표 지점으로 원본과 래퍼를 각각 실행하여 비교해야 한다.
기본 DLL 교체 방식에서는 EXE 해시가 원본과 동일하므로 해시만으로 그래픽 경로를 구별할 수 없다.
게임을 종료한 상태에서 기존 ddraw.dll과 HQCDD를 번갈아 배치하고,
각 표본에 로드된 DLL 경로·해시·버전 및 dxwrapper/syw2x 사용 여부를 기록한다.
비교용 prepare.py 복사본은 기존 DLL을 보존하며 나란히 실행 경로를 구분할 때 사용할 수 있다.
게임을 활성 상태로 유지하고 일시정지·메뉴·전투 전환이 포함된 표본은 버린다.
렌더러 FPS와 시뮬레이션 틱 횟수를 구분하며 VSync/임의 60FPS 제한을 속도 복원으로 취급하지 않는다.
