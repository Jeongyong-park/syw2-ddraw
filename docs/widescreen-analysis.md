# 와이드 전장 구현: 1차 분석과 격리 시제품

대상: `[ESL]Syw2plus 2606.exe`
SHA-256: `716dde6a1cd837c74c83c426fba634491143d624c0c284aad4dc4d5d5ea2417f`.
현재 게임용 옵션은 구현되지 않았다. 원본 EXE와 실행 중인 게임은 수정하지 않았다.

## 재현 도구

`tools/widescreen_probe.py`는 해시를 확인한 뒤 원본 x86 함수를 Unicorn 메모리에서 실행한다.
해상도 상수 변경도 에뮬레이터 내부에만 적용한다. 파일 패치 또는 게임 실행 기능은 없다.
`pefile`, `unicorn`이 필요하다. 선택적 Ghidra 연결은 로컬 서버에서 읽기 전용 조회만 수행한다.

```powershell
python tools/widescreen_probe.py "D:\[ESL]Syw2plus\[ESL]Syw2plus 2606.exe" --width 1068 --output output/widescreen-probe-1068 --ghidra-url http://127.0.0.1:8089
```

분석 도구는 `D:\sdk\ghidra-mcp`의 플러그인 API와 열린 동일 이름의 프로그램을 사용했다.
Ghidra 조회는 현재 프로그램 이름을 확인하며, 실행 검증 대상의 일치는 EXE SHA-256으로 제한한다.
Ghidra 원본 바이너리 해시를 API로 대조한 것은 아니므로 디컴파일 결과의 핵심은 원본 명령 실행과 함께 확인했다.

## 확인한 지점

| 주소 | 확인 내용 |
|---|---|
| `0041B4DA` | 전장 진입의 해상도 모드 인자 `push 3`; SYW2X 확장 ON은 4로 변경 |
| `004644A0` | 해상도 모드 설정 함수; 3은 800×600×8, 4는 원래 1024×768×8 |
| `0046452C`, `00464533` | 모드 4의 너비·높이 immediate 값; SYW2X도 이 위치를 변경 |
| `00465130` | 렌더링 객체의 클립 사각형 설정 |
| `00B3AC80`~`00B3AC8C` | 전장 좌표 사각형; 초기 우측/하단은 831/511 (inclusive), 즉 832×512 |
| `004A4860` | 화면 좌표를 카메라 기준 월드 좌표로 변환 |
| `004324E0` | 전장 캐시 갱신·스크롤·변경 블록 처리 |
| `00BA3D30` | 832×512 전장 캐시; 바로 다음 객체 `00C0BD30`까지 425,984바이트 |
| `0105796C` | 변경 블록 표; 열 우선 `column*16+row`, 기존 13×16 블록 |
| `0041BF20` | 캐시를 전장 surface로 복사; 기존 복사 크기는 832×512 |
| `00466280` | 캐시 픽셀 복사 함수; 8-bit에서 너비와 pitch를 4로 나누어 dword 복사 |
| `004922D0` | 전장 surface 생성; 일부 크기는 현재 화면 너비에서 파생 |
| `004B5960` | `screenPt_plus.dat`의 HUD 배치값 로딩 |

`004324E0`에는 스크롤 방향별 고정 복사 길이(예: `0x61800`)와 캐시 내부 포인터,
13열 반복 및 변경 블록 표 접근이 함께 존재한다. 캐시 시작 주소만 옮기는 것으로 충분하지 않다.
`004351D0` 등 지형 그리기 함수도 변경 블록 표를 직접 참조한다.

## 격리 실행 결과

- 원본 모드 3: DirectDraw 호출 직전 인자 800×600×8 확인.
- 모드 4 상수만 변경한 시제품: 1068×600×8 확인. 같은 메모리에서 모드 3은 800×600 유지.
- 전장 사각형을 넓혔을 때 카메라 중앙의 월드 좌표는 유지되고 좌우 좌표 범위가 확장됨.
- 원본 복사 함수에 서로 다른 픽셀을 가진 2행을 입력해 검사:
  1067픽셀은 6바이트 불일치, 1068 및 1088픽셀은 전 픽셀 일치. 뒤쪽 보호 영역은 유지됨.

따라서 첫 구현의 표시 크기는 **1068×600**, HUD 가로 오프셋은 **134**로 조정한다.
내부 전장 캐시는 64×32 블록 단위에 맞춰 **1088×512**, 변경 표는 **17×16**으로 잡는다.
512 높이는 기존 전장 캐시 기준이다. HUD 양옆의 하단까지 지형을 표시하는 단계에서는
캐시 높이 및 관련 루프도 추가로 확장해야 하므로 현 시제품을 최종 전장 전체로 간주하지 않는다.

## 구현한 캐시 컴포넌트

`tests/support/wide_terrain_model.h`(당시 `src/widescreen.h`)의 `WideTerrain`은 별도 캐시 메모리, 변경 블록 표시,
겹치는 영역의 방향별 스크롤, source pitch 1088에서 다른 destination pitch로 1068픽셀을
복사하는 함수를 제공한다. 아직 엔진에 연결하지 않았다.

`widescreen_test`에서 512행 전체 복사·행 패딩/후미 보호·잘못된 크기 거부·마지막 블록·
8방향 및 정지 스크롤을 독립 참조 결과와 비교했다. 이 검사는 실제 지형 렌더링이나
캐시의 엔진 연결을 검증하지 않는다. 스크롤 시 변경 표는 보수적으로 전체 갱신한다.

## 원본 캐시 경로 검증과 Windows 실행

`tools/widescreen_cache_probe.py`는 원본 코드의 94개 피연산자를 검증 후 Unicorn
메모리에서 재배치한다. 8방향 스크롤의 유지 픽셀과 노출 영역 변경 표를 독립 모델과
비교했고, 이전 캐시와 새 버퍼의 보호 영역이 유지됐다. 원본 `0041BF20`에서
`00466280`으로 이어지는 복사 경로의 557,056픽셀이 일치했다. 지형 그리기 경로
5곳도 새 변경 표의 마지막 열을 참조했다. 지형 타일 렌더링 전체를 검증한 결과는 아니다.
결과는 `output/widescreen-cache-probe/report.json`에 기록한다.

`tools/prepare_widescreen_prototype.py`는 저장소 `output/` 안의 게임 사본에만
별도 EXE를 생성한다. 원본 SHA-256 및 각 패치 전 바이트를 확인하고 기존 파일을
덮어쓰지 않는다. 표시 모드·카메라 경계 7개 변경을 추가하며 `.hqwide` BSS에
캐시와 변경 표를 배치한다. 이 도구는 배포용 설치 프로그램이 아니다.

첫 실험 파일은 섹션 사이 주소 공백 때문에 Windows 실행 오류 193이 발생했다.
추가 섹션을 기존 마지막 섹션의 정렬된 끝에서 시작하도록 수정한 v2 사본은
실제 Windows에서 실행되어 800×600 메뉴와 ASI 출력을 확인했다.
이후 사용자가 전장에 진입했고 로그에서 `SetDisplayMode 1068x600 8-bit`와
1088×600 전장 surface 생성을 확인했다. 사용자 화면과 별도 창 캡처에는 전장이
표시되지만 HUD는 왼쪽에 남아 있고 하단 오른쪽은 비어 있다. 동일 카메라의
4:3 비교, 전체 가장자리 지형, HUD 중앙 정렬 및 클릭 좌표 검증은 남아 있다.

사용자가 커서가 보이지 않는 문제를 제보했다. 실행 중 읽기 전용 조회에서
`0066976C`는 1, 커서 좌표 `00C0CB58/5C`는 (687, 251)이었다.
`00437C90`은 해당 좌표로 primary surface를 잠그고 `00419DE0`을 통해
소프트웨어 커서를 그린다. 따라서 입력 정지나 Windows 커서 카운터만을
원인으로 단정하지 않는다. 커서 스프라이트·최종 합성 경로를 추가 확인해야 한다.
GDI로 시작했으며 사용자가 GPU로 전환한 뒤 프로세스는 종료 코드 0으로 종료됐다.
후속 사용자 녹화에서 GPU 전환 후 커서가 표시되는 장면을 확인했다.

### 사용자 플레이 녹화 검토

제공 파일: `녹음 2026-09-11 215036.mp4` (로컬 사용자 제공, 저장소에 포함하지 않음).
영상 정보는 3840×2160, 30fps, 56.3초다. 이는 녹화 프레임률이며 게임 출력 FPS가 아니다.
시간대별 프레임은 로컬 `output/widescreen-video/`에 추출했다.

- 5초: 디스플레이 설정에서 GDI 선택 상태가 보인다.
- 10초: GPU / Sharp Bilinear / 전체화면 선택 상태가 보인다.
- 13초: 설정이 닫힌 전장에서 붉은 게임 커서와 건설 완료 메시지가 보인다.
- 20~25초: 본영에서 다른 지형으로 카메라가 이동하고 미니맵 시야 표시가 달라진다.
- 30초: 본영 선택 정보와 생산 진행률 53%, 붉은 커서가 보인다.
- 35~55초: 선택 정보, 유닛 위치, 건설 중 건물의 상태가 변화한다.

따라서 와이드 프로토타입의 실제 플레이와 GPU 전환 이후 커서 표시를 확인했다.
다만 설정 창 열기/닫기와 출력 전환이 함께 일어나므로 GDI 자체가 커서 미표시의
원인이라고 확정할 수는 없다. GDI/GPU 각각 새 프로세스에서 비교해야 한다.
HUD 왼쪽 정렬과 하단 오른쪽 빈 영역은 영상에도 남아 있다.
이 녹화만으로 클릭 좌표 전체, 입력 지연, 프레임 시간 또는 30유닛 이상 부하를
검증했다고 판단하지 않는다.

## HUD 좌표 공유 확인

`screenPt_plus.dat`의 `MenuStartX`는 `004B5960`에서 `009E2B74`의
16-bit 값으로 읽힌다. `0049ACC0`의 아이콘 그리기와 `00498C20`의 마우스
영역 판정이 같은 값을 참조한다. 이 항목은 메모리에서 X 원점을 134만큼
옮기면 그리기와 판정이 함께 이동하는 구조다. 전체 HUD나 미니맵까지 같은
방식으로 이동한다고 가정하지 않으며, 배경 surface 합성과 다른 좌표 항목은
추가 확인이 필요하다. 원본 데이터 파일은 수정하지 않았다.

`tools/widescreen_hud_probe.py`는 원본 `00498C20`을 Unicorn에서 실행한다.
명령 사용 가능 여부 조회만 대체하고 인덱스 계산과 사각형 판정은 원본 명령을
그대로 사용한다. 12개 버튼의 기본/134픽셀 이동 좌표, 내부·경계·이전 중심점
204개 검사가 통과했다. 크기와 X/Y 간격은 의도적으로 서로 다른 합성 값이며
실제 아이콘 자산 크기나 다른 HUD 항목을 검증한 것은 아니다.

같은 도구에서 원본 커서 RLE 렌더러 `00466D50`도 실행한다. 투명 픽셀을 포함한
합성 스프라이트를 pitch 1068/1088, 중앙·확장 영역·오른쪽 아래 경계에 그리는
6개 경우가 픽셀 단위로 일치하고 행 패딩과 후방 보호 영역을 보존했다.
따라서 이 함수가 확장 pitch를 처리하지 못한다는 가설을 뒷받침하지 않는다.
실제 커서 자산, 호출 상태, GDI/GPU 최종 출력은 이 검사 범위 밖이다.
결과: `output/widescreen-hud-probe/report.json`.

하단 배경 합성은 `0041C5C0`에서 `0104F814` surface를 전장 surface로
`BltFast(x=0, y=화면 높이-HUD 높이)` 하는 경로다. 명령 그리기 전에 실행되며,
배경 폭을 800으로 제한하고 목적지 X를 134로 옮기는 작업이 별도로 필요하다.
종족별 장식 스프라이트도 이 함수에서 X=0 또는 29에 추가로 그린다.
이 항목을 무시하고 좌표 파일만 바꾸면 배경과 장식이 버튼과 어긋난다.
### 하단 배경·명령 영역의 첫 연결

`prepare_widescreen_prototype.py --hud-preview`는 별도의 실험용 EXE에
하단 배경 폭 800, 목적지 X=134와 명령/단축키 버튼 원점 보정을 추가한다.
`0041C603`의 BltFast 인자 구성은 새 실행 섹션 `.hqcode`로 옮겨 imm32 X를
전달한다. `0041B555`는 원본 바이트상 로더로의 tail jump이므로 이 호출 규약을
보존한 중계 코드를 사용한다. Ghidra의 호출 표기만 믿지 않고 실제 바이트로 검증했다.
좌표 파일은 게임 실행 중 추출되고 종료 시 사라지므로 파일을 바꾸지 않고,
원본 로더 실행 직후 `009E2B74`와 `009E2B84`에 각각 134를 더한다.

생성 파일: `output/widescreen-live/game/HQCDD-wide-hud-preview.exe`.
`verify_widescreen_hud_preview.py`로 생성 파일의 실제 중계 코드를 실행하여
배경 목적지 (134,397), 원본 영역 (0,0,800,203), 명령 원점 (786,486),
단축키 원점 (405,493), 두 번 재로딩 시 이동량 비누적과 스택 복귀를 확인했다.
Windows `CreateFileMappingW(SEC_IMAGE)`도 오류 없이 수용했다.
이는 가상 COM/좌표 로더를 사용하는 검사이며 실게임 표시 검증은 아니다.

**부분 연결 상태다.** 미니맵, 초상화, 상태 글자, 종족 장식, 상단 자원,
하단 양옆 지형은 아직 이동/확장하지 않았다. 이 파일을 완성된 중앙 HUD로
배포하거나 기존 실험 파일 대신 자동 실행하지 않는다.

### 하단 HUD 확장 및 사용자 화면 확인

후속 `HQCDD-wide-hud-v2.exe`에는 화면 좌표 10개 항목(명령/단축키, 일반 메뉴,
초상화, 생산 정보, 체력 정보, 설정 버튼, 탑승 유닛, 인벤토리, 시계)을 연결했다.
종족 장식도 같은 X 이동을 적용했다. 미니맵과 HUD 불투명 영역 클릭은 원본
함수에 전달하기 전에 X에서 134를 뺀다. 미니맵 배경 픽셀은 HUD surface 내부
좌표를 유지하며, 전장에 직접 그리는 시야 테두리는 그 호출 동안만 원점을 옮기고
반드시 복원한다. 경고/핑 좌표는 아직 별도 검증이 필요하다.

GPU 창 모드로 v2를 실행했고 사용자가 37유닛 세이브 전장에 진입한 화면을 제공했다.
화면에서 하단 HUD가 수평 중앙에 배치되고 붉은 게임 커서와 병력이 표시된다.
이 관찰만으로 모든 버튼·종족·선택 상태가 정상이라고 확정하지 않는다.
창의 위아래 검은 여백은 기존 4:3 창 안에 와이드 출력이 들어간 상태이며,
HUD 양옆의 하단 지형 확장은 여전히 남아 있다.

`HQCDD-wide-hud-v3.exe`에는 상단 자원 아이콘/숫자, 고정 툴팁 글자,
시계 옆 장식을 추가로 이동했다. v2 실행 중인 파일을 덮어쓰지 않고 별도 생성했다.
생성된 v3에 대해 10개 필드와 주변 바이트 보존, 65개 인자 변환, 원점 복원,
실제 `004516A0`의 미니맵 클릭 3개 경우(이동한 지점의 동일 타일 반환, 이전 위치
및 왼쪽 바깥 위치 거부)가 통과했다. v3의 실게임 화면 확인은 아직 하지 않았다.

### 디스플레이 비율 선택 및 전체 높이 후속 실험

디스플레이 페이지에 `전장 비율: 4:3 / 16:9`를 추가했다. 창 모드/전체화면과
독립적이며 `[Display] BattleAspect=4:3` 또는 `16:9`로 저장한다. 버퍼와 HUD를
실행 도중 교체하지 않고 **게임 재실행 후 적용**한다. 변경 시 저장 체크가 꺼져
있으면 재실행 적용에 필요한 저장을 안내하고 적용을 중단한다.

현재 선택 기능은 새 실험 EXE의 `.hqcode` 안에 `HQASPECT` 복원 표가 있을 때만
활성화된다. 기존 v2/v3 및 원본 배포 클라이언트에서는 비활성화한다. 이 단계는
일반 배포판에 동적 와이드 패치를 설치하는 구현이 아니다. 새 실험 파일은 키가
없으면 기존 실험 동작인 16:9를 유지한다. 4:3 선택 시 첫 DirectDraw 생성 때
전장·캐시·HUD 패치 전체의 현재 바이트를 검사하고, 전부 일치할 때만 메모리를
원본으로 복원한다. 디스크의 EXE는 수정하지 않는다. 원본 바이트 불일치 또는
쓰기 권한 확보 실패 시 부분 복원을 하지 않는다. 적용은 프로세스당 한 번이다.
SYW2X `ViewPortPlusOn=0`인 격리된 실험 폴더에서 검증 중이다.

`HQCDD-wide-hud-v4.exe`는 기존 512행 캐시와 비율 선택 표를 포함한다.
124개 패치의 520바이트가 원본과 일치함을 대조했다. 네이티브 테스트는 16:9 유지,
4:3 복원, 마지막 패치 불일치 시 변경 없음, 같은 페이지의 보호 속성 복원을 확인한다.
UI 테스트는 비율 버튼의 활성 상태, 위아래 행과의 간격, SYW2X 페이지에서 숨김을 확인한다.

`HQCDD-wide-hud-v5.exe`는 `--full-height`를 추가한 후속 실험이다. 캐시는
1088×608, 화면 복사는 600행, 변경 블록 표의 열당 간격은 32행으로 확장했다.
안개·높이·변경 검사·그리기 순회 범위를 함께 늘렸고, 기존 갱신 조건을 통과한
프레임은 전체 캐시를 다시 그린다. 변화 없는 프레임은 캐시를 유지한다.
`verify_widescreen_full_height.py`는 생성 EXE의 실제 명령어로 캐시/변경 표의
앞뒤 경계, 변경 없는 경로, 다섯 지형 종류의 마지막 블록 주소, 정확히 600행만
복사하는 원본 루틴을 확인했다. 기존 HUD 중계 검증도 통과했다.

풍향계 X 보정은 v3 이후에 포함된다. v5의 하단 지형 실제 표시와 전체 재그리기
비용은 **실게임 미검증**이다. 검증된 최적화나 릴리즈 완료로 취급하지 않는다.
실행 중인 사용자 게임에는 파일 교체나 패치를 적용하지 않았다.
실험 폴더의 게임 프로세스가 모두 종료된 것을 확인한 뒤 `plugins/hqcdd.asi`를
새 빌드로 교체했고 이전 파일은 `hqcdd.asi.before-aspect`로 백업했다.
원본 설치 폴더는 변경하지 않았다. v4/v5 재실행과 양쪽 비율의 전장 검증은 남아 있다.

## 다음 구현 순서

### 원본 EXE + ASI 전환 및 피격 경고 보정

후속 ASI는 원본 파일의 SHA-256
`716dde6a1cd837c74c83c426fba634491143d624c0c284aad4dc4d5d5ea2417f`와
167개 명령어 위치를 확인하고, `BattleAspect=16:9`일 때만 실행 중 메모리를 패치한다.
일반 원본의 기본값은 4:3이다. 이전 실험 EXE의 복원 표 지원은 호환 경로로 남겼다.

고정 주소 할당은 실제 원본 프로세스에서 이미 점유된 주소 때문에 실패했다.
게임 코드가 변경되지 않고 4:3으로 실행된 것을 로그로 확인했다. 이를 해결하기 위해
OS가 고른 주소에 캐시와 중계 코드를 할당하고 절대 캐시 참조, 게임→중계 상대 점프,
중계→게임 상대 점프를 재배치한다. 최종 명세는 패치 참조 78개, 코드 참조 11개다.
실행 코드의 RX와 데이터의 RW 보호를 구분한다. 메모리는 게임 프로세스 종료까지 유지한다.

원본 EXE로 실행한 PID 35100에서 `selectable=1 wide=1`과 `1068x600`,
`1088x600` 생성 로그를 확인했다. 실제 전장 캡처
`output/widescreen-runtime-check/battle-asi.png`에서 중앙 HUD, 오른쪽 하단까지의 지형,
원형 계기 내부 풍향계를 확인했다. 왼쪽의 어두운 지역은 해당 캡처만으로 지형의 모든
경계가 정상이라고 판정하지 않았다. 장시간 성능 및 모든 UI 상태 검증은 남아 있다.

사용자는 이어서 피격 경고가 미니맵 왼쪽 바깥에 표시되는 화면을 제보했다.
`00451890`은 이벤트 발생 시 원래 미니맵 좌표를 `object+0x2BAB2`에 저장하고,
`00451920`은 이 값을 읽어 `00451A09`에서 `00419DE0`을 호출한다.
미니맵 객체의 임시 원점 이동과 별개인 저장 좌표이므로 최종 스프라이트 호출 X에
134를 더했다. 이벤트 데이터, 세이브 좌표, Y, 타이밍은 변경하지 않는다.

`verify_widescreen_alert.py`는 원본/와이드 각각 경고 없음, 첫 프레임, 프레임 진행,
종료, 반복 등 5가지 상태를 원본 루틴으로 실행했다. 최종 그리기만 캡처했으며,
X 이동량, 원점/저장 좌표/클립 복원, 애니메이션 종료·반복 상태를 확인했다.
보정 ASI로 원본 EXE를 재실행한 PID 37312에서 16:9 활성화와 피격 경고 중계의
X+134 및 원본 `00419DE0` 복귀를 메모리 읽기로 확인했다. 경고 활성 프레임도
관측했지만 캡처가 DPI 좌표 문제로 미니맵을 포함하지 못했다. 따라서 최종 표시 위치를
캡처로 검증했다고 보지 않는다. 해당 게임은 이후 종료 코드 0으로 종료됐다.

### 4:3 / 16:9 혼합 멀티플레이 검증 상태

혼합 비율의 락스텝 안전성은 아직 검증하지 않았다. 명령·난수·시뮬레이션 틱을
직접 바꾸는 패치는 없지만, 화면 확장에 따라 카메라 영역의 안개/타일 보간 갱신 범위가
변경된다. `004A33A0`은 타일당 16비트의 네 4비트 값을 갱신하고 `004A3510`이 읽는다.
현재 확인한 쓰기 호출은 `004324E0`의 지형 갱신 루틴이며, 읽기는 이 루틴과
`00435400`, `004A34A0` 등이다. 이를 게임의 실제 지형 높이나 권위 있는 시야 데이터라고
단정하지 않는다. 저장 대상 영역에 포함된다는 사실만으로 동기화 대상이라고도 볼 수 없다.

검증 시 4:3/4:3 기준과 4:3/16:9 조합에 같은 초기 상태·난수·게임 명령을 넣고
같은 시뮬레이션 틱의 유닛 위치/체력/자원/난수 상태를 비교해야 한다. 카메라와
렌더링 캐시는 클라이언트별로 달라도 되므로 전체 메모리나 저장 파일 해시를 그대로
비교하면 안 된다. 화면 밖 전투, 안개 경계, 카메라 이동, 37유닛 이상 전투를 포함한다.
또한 16:9의 전체 지형 재그리기 비용으로 틱 처리가 늦어져 생기는 대기와 실제 상태
불일치를 구분해야 한다. 혼합 멀티 호환을 릴리즈 보장 사항으로 기재하지 않는다.

### 검증 범위와 후속 작업

#### 혼합 비율: 추가한 자동 비교의 범위

`tools/verify_widescreen_visibility.py`는 원본과 v6 실험 이미지를 독립적인
Unicorn 인스턴스로 실행한다. 6개 카메라/플레이어 조합에서 원본 시야 갱신 함수
`00417FE0`, `00418160`, `00418080`, `00418200`, `004182A0`에 같은 합성 입력을
넣었다. 모드당 228회 실행 후 각 단계에서 8인 시야 배열 `0089D58E`의
259,200바이트가 일치했다. 37개 스텐실 입력은 실제 37유닛 전투 테스트가 아니다.

안개 전처리 `004324E0..00432911`의 모든 쓰기를 추적했으며, 허용한 파생 안개
보간 배열 `008DCA0E`, 표시 갱신 배열 `008EC72E`, 이전 안개 배열 `00B94010`,
카메라 재그리기 플래그와 스택 이외의 쓰기는 없었다. 전처리는 원본 시야 배열을
변경하지 않았다. 파생 안개 값은 비율별로 실제 달라져 서로 다른 범위를 검사했다.
중앙 카메라에서 갱신 타일은 1,024개에서 4,096개로 증가했다. 이는 작업량 관측이며
실제 FPS나 시뮬레이션 틱 지연 측정은 아니다. 전체 렌더러의 쓰기 안전성도 뜻하지 않는다.

전송 경로는 `00439FA0 → 00439E80 → 0046B300 → IDirectPlay4A::SendEx`다.
GUID `0AB1C531-4745-11D1-A7A1-0000F803ABFC`와 32비트 vtable 오프셋 `0xC4`를
[Wine의 DirectPlay 헤더](https://github.com/wine-mirror/wine/blob/master/include/dplay.h)와
대조했다. 이 경로를 HQNET 채팅용 Winsock 전송과 구분했다.

`tools/verify_widescreen_messages.py`는 메시지 `0x103`, `0x107`, `0x10D`, `0x112`의
원본 디스패치와 헤더 변경, `0x103`의 실제 전역 큐 `00632C08` 삽입을 실행한다.
호스트/참가자 각각과 페이로드 0/4/120바이트를 조합한 24개 비교에서 원본/와이드의
패킷 바이트, 수신 대상, 플래그, 큐 데이터가 일치했다. 연결 상태·호스트 조회와
전송 경계는 대체했으며 실제 DirectPlay 통신을 수행하지 않았다. 큐 한 번 삽입만
검사했으므로 큐 포화, 재전송, 명령 생성, 수신 처리, 전투/AI/틱의 결정성은 미검증이다.

로컬 결과는 `output/widescreen-runtime-check/visibility-scope.json` 및
`message-scope.json`에 있다. 두 스크립트는 원본 EXE와 v6 실험 EXE를 위치 인자로,
`--report`로 JSON 저장 경로를 받으며 pefile과 Unicorn이 필요하다. 게임 이미지가
필요한 선택적 로컬 검사이며 배포 CI의 게임 없는 네이티브 테스트를 대체하지 않는다.

현재 결론은 **검사한 시야 전처리와 송신 구간에서 비율에 따른 상태 불일치를 찾지
못했음**이다. 혼합 멀티 호환 보장은 여전히 보류한다. 후속 검증은 같은 게임/패치
버전의 두 클라이언트로 4:3/4:3 기준과 4:3/16:9를 비교하고, 같은 틱의 유닛 위치,
체력, 자원, 난수 상태 및 명령 순서를 계측해야 한다. 서로 다른 카메라, 화면 밖 전투,
시야 경계와 37유닛 이상 전투를 포함하며 렌더링 지연과 상태 불일치를 따로 기록한다.

아래 목록은 초기 구현 순서의 기록이다. 현재 완료 범위와 남은 검증은
[와이드 모드 안내](widescreen.md)를 기준으로 확인한다.

1. 캐시 내부 오프셋까지 포함한 모든 참조와 스크롤 복사·변경 표를 새 메모리로 연결.
2. 전장 진입/퇴장과 SYW2X 확장 충돌 검사, 원본 바이트 검증 및 부분 패치 방지.
3. 별도 게임 사본에서 실제 좌우 지형·유닛·안개 렌더링 확인.
4. HUD 원점 및 입력 조정, 하단 양옆의 지형 처리.
5. 옵션 노출과 37유닛 이상 전장 성능 비교.

격리된 해상도·좌표·복사 함수의 성공을 실제 게임 와이드 모드의 성공으로 확대하지 않는다.
